# 系統架構與工作邊界（草案 v0.1）

## 資料流

1. 租客由 Nuxt 網頁選指定視角並拍照。E 統整頁面，A 負責拍照引導元件及品質判讀。
2. FastAPI 暫存新照片，呼叫 A 的品質檢查。A 回傳 `accepted`、`retake` 或 `manual_review`。只有合格照進入正常後續判讀；其餘先補拍或人工處理。
3. D 在確認合格後，將照片存入 Object Storage，於 PostgreSQL 建立照片紀錄，保存訂單、車輛、拍攝視角、用途與時間。
4. 取還車同車同部位的車外照片由 B 比較；合格的車內外照片由 C 分級。若沒有可比較的取車基準照，B 回傳 `uncomparable`。
5. D 儲存判讀與可見依據，建立清潔或待覆核車損事件，依規則更新車況並分流。**疑似車損或尚未排除的車損不確定案例，整車不進群包清潔任務池。**
6. 只有清潔需求時，D 依任務難度、資格、距離及預估完成時間處理可用官方人員和合格會員的媒合，不預設官方優先。本次租客自行補救沿原訂單處理且無群包獎勵；其他會員接單另建任務。
7. 整備前後照片留證；完成照再次呼叫 C。複檢未通過不結案、不給獎勵；只有所有停租原因解除，車輛才能恢復可租。

## 負責範圍

| 角色 | 必須交付 | 不直接負責 |
| --- | --- | --- |
| A | 六視角引導及品質檢查函式，重拍理由，拍照元件與 E 接合 | 清潔／車損判斷、寫事件資料表 |
| B | 取還車局部對齊、疑似差異標記、無法比較時的原因 | 最終車損定責、事件派工 |
| C | 車內外整潔三級準則、判讀函式、整備後重複判讀、驗證案例 | 自動收費、會員獎勵 |
| D | API、資料與照片存取、事件狀態、分流、任務、獎勵示意、整合 | A／B／C 的模型實作、E 的畫面 |
| E | 租客、營運、會員介面，與 A 的拍照元件整合、六種示範操作 | 直接寫資料庫、在瀏覽器放模型金鑰 |

## 資料歸屬

- **PostgreSQL**：會員／角色、車輛、訂單、照片中繼資料、判讀結果、事件、任務、驗收、獎勵與狀態歷史。具體表格由 D 在 FastAPI 階段定稿。
- **Object Storage**：有授權的展示基準照、操作上傳的照片、整備前後照、B 產生的標記圖；資料庫保存 object key，不儲存公開永久網址。
- **開發／評估照片**：由 A、B、C 在本地或授權環境使用；只把有再散布權的小量示範資料放 `demo_data/`。開發用全量照片不需要全上正式儲存。
- **模型權重／金鑰**：不得把 API 金鑰寫入網頁或 Git；大型權重以合法來源與下載／產製說明重現。

## 開發與展示

- 本地：每人快速迭代；D 的假結果先符合相同模組契約。
- 線上測試：完整流程能跑後，提供組員共用網址；測試資料與正式展示資料分開。
- 正式展示：Nuxt 與 FastAPI 部署在能執行程式的服務；Neon 只提供 PostgreSQL 與 Object Storage。評審在主辦方電腦以瀏覽器操作，不依賴組員電腦常駐。
- B 的 DINOv2 在線上服務的記憶體與延遲尚未測量；部署選型依實測決定，展示不可把預先計算冒充即時推論。

## 尚待全組決定

- 拍照視角分類與車牌辨識屬選配；若未做視角分類，不可宣稱系統可自動指出拍錯部位。
- 清潔三級實際判準、人工覆核與費用減免條件；原型不自動收費或定責。
- 線上 Nuxt 與 FastAPI 的運行平台、DINOv2 所需記憶體與時間。
- 示範資料的使用授權、是否需要遮蔽車牌與人臉。
